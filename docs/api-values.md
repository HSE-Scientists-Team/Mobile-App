# Значения, которые задаёт клиент (коды)

Статус на 2026-10-19. Решение пользователя: в Gateway API **нет перечислений**; поля, у которых в `docs/openapi.yaml` стоит просто
`type: string`, задаём мы, по дизайну, а на сервер отправляем **числовое значение** (строка из цифр, у кодов начало с 1). Всё, чего не
хватает в бэкенде, игнорируем: включён весь функционал первого спринта, для которого есть ручки; неизвестные значения в ответах не мешают
(читаются как «неизвестно» и не прячут сами записи). Тестирует пользователь на реальном сервере; значения, которые сервер понимает иначе,
правятся здесь и в одном месте кода.

Документ — контракт для `domain-data`, `compose-ui` и `tester`. Что в реестре `docs/api-gaps.md` закрыто этим решением, а что нет, см. раздел
«Что остаётся открытым» ниже.

## 1. Правила

1. **Запрос.** Код отправляется строкой из цифр (`"1"`). Неизвестного значения не отправляем никогда.
2. **Ответ.** Код читается точным совпадением после `trim()`. Всё остальное (пусто, другая строка, незнакомое число) — `null`: «неизвестно». Из-за
   неизвестного значения запись не скрывается и не теряется, пропадает только то, что без значения не нарисовать (чип, подпись).
3. **Единое место.** Таблица кодов каждого значения живёт в одном месте (раздел 2), коды не переиспользуются и не перенумеровываются.
4. **Помечаем непроверенное.** Коды, которые сервер сам интерпретирует (`action`, `status`), на сервере не проверены: `ProjectActions` помечен
   `@UnverifiedContract` (он в `:gateway`), у `ProjectStatus` в `:common` пометка только в KDoc «не подтверждено бэкендом». Если сервер понимает иначе, правка идёт в одном объекте.

## 2. Таблицы кодов

| Значение | Где в API | Код → смысл (по дизайну) | Где в коде |
|---|---|---|---|
| Тип проекта | `Project.type` (в `ProjectCreate` обязателен), параметр `type` поиска; `project_types` профиля (массив); параметр `project_type` поиска людей | `1` Scientific «Научный», `2` Practical «Проектный» | `ProjectType.code` и `ProjectType.fromCode()` в `:common` |
| Статус проекта (только чтение) | `Project.status` | `1` Recruiting «Набор открыт», `2` Unpublished «Снят с публикации». Другие значения сервера — `null` | `ProjectStatus.code` и `fromCode()` в `:common` |
| Срок проекта (фильтр) | параметр `duration` поиска | `1` UpTo3Months «до 3 мес», `2` From3To6Months «3–6 мес», `3` Over6Months «6+ мес» | `ProjectDuration.code` в `:feature:projectsearch:domain` |
| Сфера | `Project.field`, параметр `field` поиска | `1` Computer Science, `2` Data Science, `3` Инженерия, `4` Математика, `5` Физика, `6` Химия, `7` Биология, `8` Медицина, `9` Экономика, `10` Социология, `11` Лингвистика, `12` Дизайн | `Spheres` в `:common` (переезжает из `SphereCatalog` модуля `projects:data`); `Sphere.id` — код, `Sphere.name` — подпись |
| Действие перехода | `ProjectTransitionRequest.action` | `1` Publish «опубликовать», `2` Pause «приостановить набор» (в приложении это «Снять с публикации»). Порядок взят из `summary` метода: «опубликовать, приостановить набор, начать, завершить или отменить»; `3` начать, `4` завершить, `5` отменить приложением не используются | `ProjectActions` в `:gateway` (`contract`, `@UnverifiedContract`) |
| Уровень обучения | `study_level` | остаётся **свободным текстом** (поле текстовое в макете), кода нет | — |

Даты проекта (`planned_start`, `planned_end`): строка ISO-даты `YYYY-MM-DD`. Начало — первое число месяца начала, конец — последнее число месяца
окончания. Чтение: берутся `YYYY-MM` из начала строки (подходит и `YYYY-MM-DD`, и дата со временем); не разобралось — `period = null`.
Функции форматирования и разбора — в `:gateway/mapping/ProjectDates.kt`.

## 3. Что включаем (флаги возможностей источников Gateway)

| Флаг | Было | Станет | Что делает |
|---|---|---|---|
| `ProjectsCapabilities.canCreate` | `false` (G40, G43) | `true` | `POST /projects`: `title`, `type`, `field`, `problem`, `goal`, `tags`, `planned_start`, `planned_end`, `roles` (каждая роль: `title`, `skills`, `slots = 1`) |
| `ProjectsCapabilities.canListMine` | `false` (G44) | `true` | «Я инициатор»: `GET /projects` (каталог и мои проекты) страницами по 100 до 10 страниц, без `mine` и `profile_user_id`; остаются проекты с `owner_user_id` = пользователь сессии; порядок сервера |
| `ProjectsCapabilities.canUnpublish` | `false` (G42) | `true` | `POST /projects/{id}/transitions` с `action = "2"` и `expected_revision` из кэша |
| `ProjectSearchCapabilities.typeFilter` | `false` (G40) | `true` | параметр `type` поиска |
| `ProjectSearchCapabilities.durationFilter` | `false` (G45) | `true` | параметр `duration` поиска |
| `CollaboratorsCapabilities.projectTypeFilter` | `false` (G11) | `true` | параметр `project_type` поиска людей |
| `ProfileCapabilities.interestTypes` | `false` (G11) | `true` | `project_types` профиля: читаем коды, пишем коды |
| `ProfileCapabilities.verificationStatuses` | `false` (G12) | **остаётся `false`** | статус работ и документов пишет сервер, его значений мы не знаем, задать их с нашей стороны нельзя |

**Фильтры с несколькими чипами.** Параметры `type`, `duration`, `project_type` в API — одна строка. Отправляем код, только когда выбран **ровно один**
чип; ноль или несколько — параметр не отправляется (два типа из двух — это и есть «любой»). Для `duration` выбор двух из трёх так не выразить:
это известное ограничение, сервер вернёт больше, чем выбрано.

**Поле `field`** в поиске и при создании — код сферы (`"1"`..`"12"`), а не название.

**Профиль.** `project_types` пишется кодами; коды, которых мы не знаем, при сохранении профиля возвращаются на сервер как пришли (данные других
клиентов не теряем). Верхний предел курса `study_year` (`MaxStudyYear = 6`) убран: «ориентируемся на сервер»; остаётся только `>= 1`.

## 4. Поведение при неизвестных значениях

- `Project.type`, `Project.status`, `Project.period`, `Project.sphere` — nullable; `null` = неизвестно, чипа или строки нет, сам проект показывается.
- Проект с неизвестным статусом **не прячется** ни в поиске, ни в «Я инициатор». Действие «Снять с публикации» для своего проекта предлагается, пока
  статус не `Unpublished` (то есть и при неизвестном).
- Неизвестные `project_types` профиля не показываются как чипы, но сохраняются при записи (см. выше).
- Статусы работ и документов (G12), `author_role` отзыва (G13), `ProjectMember.status` (G52): остаются «неизвестно».

## 5. Решения по неясному

| Вопрос | Решение | Где менять |
|---|---|---|
| Формат `planned_*` | ISO-дата `YYYY-MM-DD` | `ProjectDates.kt` |
| Какое действие — «Снять с публикации» | `Pause = 2` («приостановить набор»), не «отменить» | `ProjectActions` |
| Как получить «мои проекты» без `mine` | `GET /projects`, фильтр по `owner_user_id` на клиенте | `GatewayProjectsDataSource.observeMyProjects` |
| Сфера числом или названием | числом | `Spheres` |
| Пустой `roles` при создании | роли необязательны (допущение спринта 1): отправляется `roles: []`; в спецификации у `roles` нет `minItems`, принимает ли сервер пустой массив — не проверено. Если откажет (400), добавим ошибку «нужна роль» | `ProjectDraft` |

## 6. Что остаётся открытым (бэкенд не ответил, мы не знаем)

Статусы работ и документов (G12) и всё, что на них стоит: чипы, очередь проверки, результаты, бейдж вкладки; значения, которые сервер пишет
сам (`Project.status` другими числами, `author_role`, `ProjectMember.status`, `ProjectJoinRequest.type/status`); семантика `mine` и
`profile_user_id`; формат дат и `action` проверены только по тексту спецификации. Весь список вопросов к бэкенду — отдельный документ.
