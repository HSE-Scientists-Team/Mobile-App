# Диплинки: что нужно от бэкенда и веб-части

Статус на 2026-10-20. Адресат: команда бэкенда (`matchlab-backend`) и тот, кто отвечает за сайт `matchlab.space`. Контекст и поведение
приложения — `docs/deeplinks.md`; здесь только то, что нужно сделать на стороне сервера, и чего приложение от него ожидает.

## 1. Что делает приложение

Пользователь регистрируется, получает письмо со ссылкой и нажимает на неё на телефоне. Вместо браузера открывается приложение, берёт `token`
из ссылки и сам вызывает `POST /api/v1/auth/email/confirm`. Если приложение помнит пароль регистрации, оно тут же входит; иначе показывает
экран входа с пометкой «Почта подтверждена».

Ссылка, которую приложение считает «своей» (строго, любое отличие — не наша ссылка и отбрасывается):

```
https://matchlab.space/verify-email?token=<токен>
```

| Часть | Требование |
|---|---|
| Схема | только `https` (`http` не принимается) |
| Хост | ровно `matchlab.space` (без `www.`, без порта, без `user@`) |
| Путь | `/verify-email` или `/verify-email/` |
| Запрос | параметр `token`, непустой, без `%`-экранирования и пробелов (base64url его не требует) |
| Фрагмент `#…` | не допускается |

Это ровно то, что сейчас собирает `internal/mail/smtp/sender.go` (`verification_url` + `query.Set("token", token)`). Менять ничего не нужно, если
сохранить формат.

## 2. Что нужно сделать

### 2.1. Android App Links — обязательно

Файл **`https://matchlab.space/.well-known/assetlinks.json`**:

- отдаётся по HTTPS, статус `200`, **без редиректов** (в том числе `http` → `https` и `www` → без `www` для этого пути);
- `Content-Type: application/json`;
- доступен без авторизации и без cookies, не режется WAF, ботозащитой и CDN-правилами «только браузеры»;
- содержимое:

```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "org.matchlab.academic_net",
    "sha256_cert_fingerprints": [
      "00:2D:35:39:2C:DB:2F:E0:13:C4:46:8E:0F:DE:0A:AB:DE:FE:47:7E:F6:B8:9F:3C:07:4D:9C:90:98:A4:6D:37",
      "<SHA-256 релизного ключа подписи>",
      "<SHA-256 ключа Play App Signing, если публикуем через Google Play>"
    ]
  }
}]
```

Первый отпечаток — отладочный ключ разработчика (для проверки до релиза). Релизные отпечатки отдаёт тот, кто подписывает сборку (Play Console →
Release → Setup → App signing). Без файла ссылка работает, но открывается в браузере или через системный выбор приложения.

Важно: Google кэширует этот файл, правки применяются не мгновенно; проверка идёт при установке приложения и периодически потом.

### 2.2. iOS Universal Links — когда подключим iOS

Файл **`https://matchlab.space/.well-known/apple-app-site-association`** (без расширения): `200`, `Content-Type: application/json`, без редиректов,
без подписи:

```json
{
  "applinks": {
    "details": [{
      "appIDs": ["<TeamID>.org.matchlab.academic_net.AcademicNet<TEAM_ID>"],
      "components": [{ "/": "/verify-email*" }]
    }]
  }
}
```

Нужны Team ID Apple Developer и итоговый bundle id (в проекте он собирается из шаблона `org.matchlab.academic_net.AcademicNet$(TEAM_ID)` в
`iosApp/Configuration/Config.xcconfig`, то есть сначала надо определиться с Team ID). iOS: ссылка, набранная в Safari вручную на том же домене, не
открывает приложение (только нажатие в письме, сообщениях, других приложениях) — это поведение системы.

### 2.3. Письмо — не ломать ссылку

- Оставить формат `https://matchlab.space/verify-email?token=…` (параметр именно `token`, путь именно `/verify-email`). Любые другие поля в
  запросе допустимы, фрагмент `#…` — нет.
- **Не оборачивать ссылку в трекинг почтового сервиса** (ссылки вида `https://click.example.com/?u=…` с редиректом). Они ломают App Links: система
  видит чужой хост и открывает браузер. Если почтовый релей включает click tracking по умолчанию — выключить для этого письма.
- Не менять `verification_url` на другой хост или путь без согласования: тогда обновляются манифест приложения, `assetlinks.json` и AASA.
- Кастомная схема (`matchlab://…`) в письмо не годится: почтовые клиенты её не показывают ссылкой, а `smtp.verification_url` проверяет только
  `http`/`https`.

### 2.4. Веб-страница `/verify-email` остаётся

Приложения может не быть (десктоп, чужой телефон, ссылка не прошла проверку). Страница, как сейчас, берёт `token` и вызывает
`POST /api/v1/auth/email/confirm`, показывает результат. Рекомендации:

- кнопка «Открыть в приложении» для телефона (на Android — `intent://` или обычная ссылка на тот же https-адрес, после успешной проверки App Links
  система откроет приложение; на iOS то же через universal link);
- страница **не должна автоматически тратить токен** там, где можно предположить, что ссылку откроет приложение (например, показывать кнопку «Подтвердить
  почту» вместо автозапроса на загрузке). Токен одноразовый: если страница и приложение обращаются к нему одновременно, один из запросов получит `404`.
  Если автоподтверждение на странице обязательно, приложение корректно покажет «ссылка уже использована», но пользователь будет подтверждён;
- `Referrer-Policy: no-referrer` и `Cache-Control: no-store` на странице: токен в URL не должен попадать в Referer и кэш.

### 2.5. API: что нужно уточнить или добавить

| № | Что | Зачем | Приоритет |
|---|---|---|---|
| A1 | `POST /auth/email/confirm` сейчас отвечает `204` без тела. Просим **возвращать подтверждённый email** (например `200 {"email":"student@hse.ru"}`) | Приложение сейчас привязывает вход к «последнему введённому адресу» и пароль регистрации ищет по нему. С адресом из ответа подстановка работает и когда пользователь успел зарегистрировать второй адрес, и показывает на экране входа правильный email | желательно |
| A2 | Зафиксировать в спецификации семантику кодов подтверждения: `404` — токен неизвестен или использован, `410` — срок истёк, `403` — домен организации недоступен, `409` — аккаунт уже есть. Сейчас они описаны, но `409` для приложения означает «уже подтверждено» (оно считает адрес подтверждённым) — подтвердите, что так и задумано | Приложение по ним выбирает текст и дальнейший шаг | нужно подтвердить |
| A3 | Повторная регистрация с тем же email делает прежнюю ссылку недействительной (`404`). Подтвердите, что в этом случае старый токен не оживёт | Приложение так и объясняет пользователю | подтвердить |
| A4 | Лимит запросов на `/auth/email/confirm` (защита от подбора токена) и его код ответа (`429`?) | Приложение сейчас покажет общую ошибку сети на `429`; нужен код и `Retry-After` | желательно |
| A5 | Опционально: обмен токена на сеанс (после подтверждения сразу вернуть `access_token`) | Пользователь, у которого приложение не помнит пароль, входил бы без ввода пароля. Решение о безопасности (одноразовая ссылка = ключ входа) за командой бэкенда; приложение готово, если появится | на решение |

## 3. Что проверить после выкладки

1. `curl -I https://matchlab.space/.well-known/assetlinks.json` — `200`, `application/json`, **нет** `Location`.
2. Google Digital Asset Links API: `https://digitalassetlinks.googleapis.com/v1/statements:list?source.web.site=https://matchlab.space&relation=delegate_permission/common.handle_all_urls`
   — в ответе пакет `org.matchlab.academic_net` и отпечатки.
3. Письмо уходит со ссылкой `https://matchlab.space/verify-email?token=…` без трекинга; ссылка в HTML и текстовой версии одинакова.
4. На телефоне с установленным приложением: нажатие на ссылку в письме открывает приложение (проверка:
   `adb shell pm get-app-links org.matchlab.academic_net` показывает `matchlab.space: verified`).
5. На телефоне без приложения и на десктопе: открывается веб-страница, подтверждение проходит.
6. Токен: повторное нажатие на ссылку после успеха даёт «ссылка использована» (`404`), по прошествии 30 минут — «ссылка устарела» (`410`).
7. Повторная регистрация того же адреса: старое письмо перестаёт работать, новое работает.

## 4. На будущее (не нужно сейчас)

Тот же механизм подойдёт для ссылок на проект и профиль (`https://matchlab.space/projects/<id>`, `/users/<id>`): достаточно добавить пути в
`assetlinks.json` (он покрывает весь домен) и в AASA (`components`). Если планируете такие страницы, зарезервируйте эти пути и не отдавайте на них
редирект на другой хост.
